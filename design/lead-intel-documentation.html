01 What the platform is

Cold outreach to local businesses fails for one reason above all others: the seller has nothing specific to say. Lead Intel exists to remove that problem. For every business in the list it answers three questions before anyone picks up the phone — is this business worth calling, what exactly is wrong with their online presence, and what should we sell them — and it answers them from measurements, each one traceable back to the page, listing or account it came from.

In non-technical terms

The operator types a trade and a place — “screen printing, Dallas”. The platform searches Google Maps across a grid of points, removes duplicates, then visits every website it found and reads it. It counts what is missing: no mobile layout, no phone number in the header, no reviews on the page, a contact form with fourteen fields, no tracking of any kind. It turns those counts into two scores, sorts the list so the best call is the first row, and writes the opening line of the call from one specific finding.

Everything above is free. Anything that costs money — a business's Google listing details, their Instagram following, whether they are running ads — is bought only for businesses the operator has ticked, on a screen that shows the price, the provider and the total first.

In technical terms

A TypeScript monorepo: a server-rendered Next.js 16 application for the operator, a Trigger.dev worker fleet for everything long-running, a Supabase Postgres database with row-level security, and a set of provider adapters (Google Places, Google PageSpeed, YouTube Data API, Apify, Google AI Studio) behind one interface each. Business logic — checks, scoring, ICP matching, deduplication, import parsing — lives in a pure package with no I/O, which is why it can carry 540 unit tests.

The rule the whole product is built on: unknown is a third answer. A business whose website could not be reached is not a business with a bad website. A business whose Instagram was never bought does not have zero followers. Every stored value can be yes, no, or nobody has looked, and the third never silently becomes one of the first two — not in a score, not in a filter, not in a chart.

02 The four stages

Every screen in the product belongs to exactly one of four stages. Two of them can cost money and two can never cost anything, and the interface says which is which at all times.

Stage 1

Sourcing

Getting businesses in: a Google Maps search for an ICP, a CSV import, or one typed by hand. Can cost

Stage 2

Filtering

Narrowing to the customers you want: your ICPs, then the filters on the leads list. Free

Stage 3

Analysis

Judging what is wrong: the crawler, 64 checks, your checklists, speed, reviews. Free

Stage 4

Enrichment

Buying what is missing: Google listing, Instagram, ads — per business, after a confirm screen. Paid

The order matters operationally: filtering and analysis are free and repeatable, so the list is narrowed and judged before a single paid lookup is made. In the data so far, 422 businesses have produced 17,943 findings for a total provider spend of $5.39.

04 How a website is analysed

Website analysis runs in two layers. The first is free, fast and used on everything; the second is a real browser and is used where it earns its cost.

Layer 1 — our own crawler Free

  1. Resolve and fetch. Three DNS attempts, robots.txt respected via robots-parser, a pinned desktop Chrome user-agent and an x-crawled-by header. HTML is capped at 12 MB; a larger document is recorded as too_big rather than failing silently.
  2. Walk the site. Home page first, then internal links classified into page types — home, services, products, pricing, about, contact — so a rule can address “the contact page” and mean it.
  3. Extract structure. Parsed with cheerio into a JSON description of the page: headings, forms and their field counts, tap-to-call links, embedded reviews, images and alt text, schema markup, social links (scanned across the whole document, not only the footer), tracking scripts, booking and chat widgets, careers links.
  4. Store evidence. Text digests, emails and phone numbers found on their own pages, the final URL, HTTP status, and the outcome of the crawl are written to field_metadata and page_audits, each with a source name and a timestamp.

Layer 2 — a real browser 0.36¢ a site

  1. Render. Playwright 1.57 (Chromium) opens the page at phone width, auto-scrolls it so lazy content loads, and measures layout facts a parser cannot see: what is above the fold, whether the page scrolls sideways, tap-target sizes, how long until main content appears.
  2. Screenshot. Home and product pages are captured, clipped to three viewports, and stored in a private Supabase Storage bucket; links to them are signed on demand and expire.
  3. Critique. The measurements — never the raw page — are handed to Gemini, which writes what those measurements miss in a sentence an operator can say on a call. See §8.
  4. Re-score. The business is scored again immediately, so a page read changes its priority in the same run.

Checklists — the operator's own definition of good

Both layers feed a checklist engine. A checklist rule names a page type, optionally an industry, a measurable field, a comparison, a value, a weight, and the sentence to say when it fails. Rules are evaluated against stored page structure, so editing a rule re-judges 347 already-read pages instantly and for free. A rule that cannot be evaluated — the page never rendered, the field was never captured — returns not checkable and is excluded from the page score rather than counted as a failure.

06 ICP rules and matching

An ICP — ideal customer profile — is the operator's own description of a customer they want. It does two jobs in one record: it is searched for on Google Maps, and it recognises businesses already in the list. Writing it once is what keeps those two halves from drifting apart.

What an ICP holds

Name and industry
What the operator calls this customer, and the trade it sits in. The industry is also what scopes checklist rules.
Search words
What a person would type into Google Maps. Several per ICP; Find businesses runs one search per word.
Word groups
Three separate lists: anywhere (business name, website text, domain, Instagram bio, Instagram category, handle, ad copy), their website only, their Instagram only.
Exclusions
Words that rule a business out, checked across every source the ICP can read — suppliers, equipment sellers and wholesalers use the same vocabulary as the customers wanted.
Conditions
Follower range, minimum Google reviews, a working website required, and places (towns or states).
Order and on/off
Lower order is checked first; the first ICP that matches wins; an ICP can be switched off without being deleted.

How matching works

  1. ICPs are sorted by order, disabled ones removed.
  2. Conditions are asked first. If an ICP requires a working website, a business whose site could not be reached is declined — and so is one nobody has ever looked at. Review floors and follower ranges behave the same way. An unanswerable condition never passes.
  3. Exclusions are checked across every source that ICP can read, not only the source that matched.
  4. Each filled word group is asked separately. requireAll = false means any group firing is enough; true means every filled group must fire — the only way to express “sells printing on their site and presents as a clothing brand on Instagram”.
  5. Term matching requires a word boundary on at least one side, so dtf matches bestpricedtf.com and dtfdallas.com but not an accidental run of letters inside an unrelated word.
  6. The first ICP to satisfy everything wins. The business stores the ICP's name, its id, and the time it was matched; the record shows which word matched and where it was found.
  7. A business that no longer fits any ICP has it cleared, not left behind. A stale label looks like a decision somebody made.

Matching reads only stored text and stored facts. It makes no network calls and costs nothing, which is what makes “edit an ICP, re-match everyone, look, edit again” a usable loop over hundreds of businesses.

Five ICPs are live today. 200 of 422 businesses sit in one; 222 match none and are kept in one place rather than deleted.

07 Scoring, priority and pitch

Two scores

Checks roll up into six areas — website quality, being found on Google, reviews and reputation, turning visitors into customers, social media, ads and tracking. Each area scores 0–100, where higher means more is wrong. 

problem = 0.6 × (worst area) + 0.4 × (weighted average of all areas)
intent  = weighted roll-up of the N family (do they already pay for things?)

Weighting the worst area at 60% is deliberate: a business with one catastrophic problem is a better call than one that is mediocre everywhere, because the call has something specific to open with.

Presence override

If a business has no website, a dead one, or only a social page, the problem score is lifted to the presence floor and the recommendation is forced to build them a website — nothing else can be sold until there is one.

Priority

Tiers, from problem score ≥ 55 and intent score ≥ 35
TierProblemIntentMeaning
1highhighLots wrong and they already spend money — call these first
2lowhighSpends money, little wrong — a harder sell
3highlowLots wrong, no sign they spend yet
4lowlowLowest priority

The spend gate

A business passes the gate at a problem score of 55 and no shared-domain warning. The gate decides where money may be spent; it never spends it. It is also the documented lever: if a run would cost too much, the cut-off is raised so fewer businesses qualify — the depth of analysis on those that do is never reduced.

What to sell them

The recommendation is the area that scored worst, mapped to one of six routes: build them a website, get them found on Google, fix their reviews, make their site convert, run their social media, set up ads and tracking. A route with no finding to show is not offered at all — the record says so, and the business is flagged for manual review instead of being given an unsupported pitch.

08 Where AI is used

Model: Google Gemini gemini-2.5-flash, called through the Google AI Studio API from a single adapter in packages/providers/src/gemini. Nothing about a business is decided by a model. Scores, priorities, ICP membership and the recommended pitch are computed by code from measurements. AI is used in exactly three optional places, and each one is a suggestion or a rewording of numbers the system already holds.

1 · Writing an ICP from a description ≈0.1¢ per use

The operator describes the customer they want in plain English or Roman Urdu — “mujhe wo log chahiye jo apna clothing brand chalate hain aur khud print bhi karte hain”. The model is given that description, the ICPs that already exist so it does not duplicate them, and real sample text from the operator's own businesses so the vocabulary comes from how these businesses actually write. It returns a draft: name, industry, Google Maps search words, the three word groups, exclusions, and one line of reasoning per term.

Guardrails: the draft is never saved. It fills the form, a mechanical check flags terms that are too generic or too short to be safe, and the preview counts what the draft would actually catch before the operator presses Save. Conditions (reviews, followers, website, places) are never suggested — they are claims about facts, so the operator sets them deliberately.

2 · Critiquing a page that a browser read 0.36¢ a site

After Playwright renders a page, the model is handed the measurements — heading structure, form fields, what sits above the fold, tap-target sizes, load timings, the page's own text digest — and asked what those measurements miss, in a sentence that can be said on a call. It is explicitly not asked to browse, to fetch, or to state facts about the business. Its answer is stored beside the page it describes, never mixed into the findings, and the checklist verdicts remain the system's own.

3 · A plain-words briefing for one business ≈0.3¢ per use

On a lead record, the operator can ask for one paragraph summarising the findings already on screen, so they can read a briefing instead of scanning a list of 20 lines before dialling. The model receives the stored findings, the scores and the business's own website text. If the model's answer cannot be parsed, or it disagrees with the operator's ICP, the record says so and the underlying findings are shown unchanged.

The standing rules for AI in this system

  • It is shown measurements; it is never asked to find facts. No model call decides whether a business has a website, how many reviews it has, or which ICP it belongs to.
  • Every call is priced and logged. AI spend appears in the same ledger as every other provider, grouped under Google AI Studio (Gemini) on the dashboard.
  • Every call is optional. The platform runs end to end with AI switched off; the three features above simply do not appear.
  • Failures are visible. A refused, unparseable or quota-limited answer is reported to the operator with the reason — never replaced with a guess.

How spending is controlled

  • A ledger row is written before the call, not after. provider_calls holds 326 rows totalling $5.39, and every figure the product shows about money is read from it.
  • Idempotency: anything already bought for a business is free the second time — the confirm screen says how many of the selected businesses are already covered.
  • Spend caps: a search carries a maximum spend and a maximum number of businesses; choosing an ICP with four search words splits the cap across the four runs rather than multiplying it.
  • Confirm screens: no paid source is ever bought as a side effect of another action.

What cannot be bought at any price, and is documented as such:

  • The list of who follows an Instagram account — Instagram publishes a follower count and never the list.
  • What a business spends on advertising — Meta publishes spend only for political and issue ads.
  • Whether a Google listing has been claimed — the field does not exist in the Places API.
  • Budget and revenue for small private businesses — no provider publishes it, which is why both filters ship switched off with that reason on hover.

Compliance note carried in the product: in the US, TCPA treats mobile numbers as residential even when they belong to a business owner, and the B2B exemption covers business landlines. That is why the owner's-mobile source is built, priced and left switched off pending a compliance review rather than quietly enabled.

Application design choices

  • Zero client-side JavaScript. Every interaction is a link, a GET form or a server action: filter menus are <details>, panels and tabs are URLs, ticking rows is a form. The result is a product that works on a slow connection and has no hydration cost.
  • One predicate, two screens. The leads list and the buy screen share matchesFilters, so “buy for all 176 shown” can never price a different set than the one on screen.
  • One source of truth for constants. Prices, thresholds, area weights and enums live in packages/shared and are read by the worker, the web app and the “How it works” page alike.

11 Engineering practice

540in the pure logic package
21applied SQL migrations
0client-side JS bundles for UI logic
  • Testing: Vitest. The core package is pure, so every check, score, tier boundary, ICP condition, dedup rule and CSV edge case is tested without a database. Provider adapters are tested against recorded responses, including failure shapes — quota exhausted, rate limited, empty body with HTTP 200.
  • Type safety: strict TypeScript across the monorepo; database types flow from the Drizzle schema; enums and prices are shared constants rather than string literals.
  • Migrations: hand-written SQL, applied through Supabase, kept in packages/db/drizzle with the reasoning in comments — including why a column was renamed rather than dropped.
  • Error philosophy: a step that could not run never looks like a step that ran fine. Failures are written to the record with their reason and surfaced on the screen the operator pressed the button on.
  • Accessibility and contrast: body text at 12.9:1 and small print at 9:1 against the page — measured, not eyeballed, after the operator reported grey text twice.
  • Documentation in place: non-obvious decisions are commented where they live; the “How it works” screen renders the product's own rules for the operator.

12 DevOps and operations

Environments

WebWorkerDatabase
Localnext dev on :3000trigger dev, development keyShared Supabase project

Trigger.dev environments are sealed from each other — a development key can only reach the local worker — but both share one database, so work started locally is visible in the deployed app. That is documented for the operator, because it also means local testing changes production data.

Deployment

  • Web: push to main on GitHub → Vercel builds and promotes. The build runs the workspace package build first (prebuild), so a type error in shared code fails the deploy rather than reaching production.
  • Worker: npm run deploy --workspace=@lead-intel/jobs builds a container image (Playwright pinned to 1.57.0 for the image's browser check) and rolls out a new version on Trigger.dev.
  • Database: migrations applied deliberately and separately, before the code that needs them.
  • Rollback: Vercel keeps previous deployments; Trigger.dev keeps previous worker versions; migrations are written to be additive where possible.

Performance engineering

The most recent operational fix is a good example of the class of problem this stack has: pages took 2–3 seconds because the Vercel functions ran in iad1 (Washington) while the database sits in ap-south-1 (Mumbai) — every query crossed the world. Pinning the functions to bom1 through vercel.json put server work at roughly 100–160 ms. The leads list was separately paginated to 50 rows, cutting a 21,000-pixel page to a sixth of its height.

Secrets and security

  • Row-level security on every table; the web app acts as the signed-in user, never as an admin.
  • The Supabase service-role key exists only in the worker's environment and in Trigger.dev's production environment — never in the web app, never in the browser, never in the repository.
  • .env files are git-ignored by name as well as by pattern; the example file carries names only.
  • Screenshots live in a private bucket and are served through short-lived signed URLs.
  • Recordings and other large media are ignored by the repository.

Observability and control

  • Every job writes progress, a running cost and a human sentence into job_runs; the operator sees it on any screen and can stop it.
  • Trigger.dev's own dashboard carries logs and run history per task.
  • The money ledger is the single source for every cost figure in the product — nothing is estimated in the interface.
